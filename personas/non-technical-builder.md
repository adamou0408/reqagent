# 非技術使用者 / Non-technical Builder

## 基本描述
- **誰是這個角色**：想要「做出一個網站 / 小工具」但不會寫程式的人。可能是產品經理、小企業主、行政人員、學生、獨立創作者等。知道自己想解決什麼問題，但無法自己寫 code、跑 CLI、或看 git diff。
- **主要職責**：在腦中（或紙上）有一個想做的 CRUD 類型網頁應用的構想，需要被引導一步步把它變成可用的東西。
- **技術熟悉度**：完全不懂（不會安裝 Node.js、不會開 terminal、也不知道什麼是 markdown）。但會上網、會用 SaaS、會用 ChatGPT/Claude 這類對話式工具。
- **使用頻率**：偶爾（每個想做的 app 可能只走一次完整流程，但中間可能會多次回頭修改）

## 核心需求
- **最在乎**：
  - **能不能真的做出一個可用的東西**（不是只拿到一份 spec 或 design doc）
  - 過程中能否**用自己的話**描述需求，而不用學 jargon（persona、user story、acceptance criteria、spec 這些字眼應該被自然地翻譯成白話）
  - 能**看到進度**：目前在整個流程的第幾步、下一步是什麼、大概還要回答幾個問題
  - 能**修改**自己之前說過的話，而不會害怕打壞已經做好的部分
- **最怕**：
  - 突然被要求「執行某個指令」或「打開 terminal」
  - 系統用自己聽不懂的語言回答（例如「spec.md 已建立」、「detect-conflicts 執行完成」）
  - 做到一半卡住、不知道自己為什麼卡住、也不知道要找誰問
  - 最後拿到的東西不能真的跑起來，或需要工程師幫忙才能上線
  - 問題被 AI 誤解，但自己看不出來是哪裡誤解了
- **典型工作場景**：
  - 打開 wrapper app，看到一個 chat 介面
  - 打字描述自己想做的東西（例如「我想要一個給寵物美容師用的預約系統」）
  - 回答 agent 的追問（誰會用、會不會需要登入、一天大概幾筆資料……）
  - 在某個 review 卡片上點「確認」或「我想改一下」
  - 最後點一個按鈕，拿到一個可以在瀏覽器裡看到的東西

## 與其他角色的關係
- **會和哪些角色互動**：
  - 對話式 agent（系統角色）—— 唯一的互動介面
  - Framework 維護者（間接）—— 不會直接見面，但維護者會透過觀察他們的 session 來改善 wrapper
- **常見的利益衝突點**：
  - 希望「快速看到成果」vs. 維護者希望「先確認 spec / conflict 再實作」的結構化流程
  - 希望「想到什麼改什麼」vs. 系統需要「維持 traceability」的紀律
  - 希望「不要問太多問題」vs. AI 需要「問到足夠資訊」才能產出可跑的 app
